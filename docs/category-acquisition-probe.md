## Pagesize 驗證（2026-10-06）

以既有 cloudscraper 與 Windows 系統 proxy 用戶端檢查職類 2002001002：pagesize=25
回 HTTP 200、25 列，API metadata 回報 lastPage=30、total=741。

職類 2003002006 的實測如下：

| pagesize | HTTP | 回傳列數 | API lastPage | API total |
|---:|---:|---:|---:|---:|
| 25 | 200 | 完成 120 頁，共 3,005 列 | 120 | 3,894 |
| 26 | 200 | 28（page 1） | 115 | 3,894 |
| 29 | 200 | 31（page 1） | 103 | 3,894 |
| 30 | 200 | 32（page 1） | 100 | 3,894 |
| 31、32、38、50、100 | 400 | — | — | — |

pagesize=30 是目前測試成功的最大值；31 已回 HTTP 400，因此職類工具預設設為 30。
API 實際回傳列數可能高於輸入的 pagesize，且 metadata 可能互相不一致，擷取器仍會
逐頁檢查並把品質不合格的批次保留在 Bronze。pagesize=21 曾在舊程序密集請求時回
HTTP 429，該值的支援狀態仍不確定。

pagesize=25 的完整職類擷取用了 120 次請求、64.83 秒、沒有 retry；回傳 3,005 列，
但 API total 為 3,894，且有 109 筆重複 jobNo、2 筆衝突，所以該批次只進 Bronze。
同一職類舊 pagesize=20 程序曾觀察到 lastPage=134；新 pagesize=30 的 page 1 回報
lastPage=100。這些不同時點的 metadata 顯示請求可能減少，但不構成完整批次的同條件
效能比較，也不能推導所有類別都會減少相同比例的請求。

舊程序在 pagesize=20、零間隔下累積大量 429 後中斷，摘要記錄 619 類中 39 類已完成、
1,437 次 retry；中斷當下的職類未發布部分頁面。初版全量續跑使用總併發 4、全域
0.4 秒間隔，後續仍遇到連續 429 而中斷；已提交類別保留，進行中的職類未發布。
最新預設間隔調整為 0.8 秒；HTTP 429 會使全域間隔倍增，連續成功後才緩慢下調。
